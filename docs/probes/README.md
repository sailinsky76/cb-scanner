# docs/probes —— 探针原始输出存档

这个目录里的每一份 `probeN.txt` 都是某个 `diag_*.py` 探针**某一次真实跑动的原始 stdout**，
一个字节没有整理过。

它们不是日志，是**出处**。项目纪律第 1 条要求「先探，别写」：凡是要新接口、新字段的，
先写探针问清楚，再决定实现。报告里每一句关于数据源的措辞——哪一列有多少行是空的、
哪个计数不随窗口变、哪两种情形分不开——都能在这里指到具体的一行。
删掉它们，那些措辞就变成了无出处的断言。

`selftest_fixes.py` 里有一条断言钉着这件事：**每一份存档都必须在 `docs/dev/HANDOFF.md`
的代码地图里被点到名**（写清楚它是哪个脚本、哪一次跑的、为什么别删）。没登记的证据等于不存在。

## 关于 probe7.txt 的乱码 —— 那不是文件损坏

`probe7.txt` 不是合法的 UTF-8，在 GitHub 上会显示成乱码或提示无法渲染。**这是刻意保留的。**

它是 `diag_sources.py` 在 Windows GBK 终端下**崩掉的现场**：脚本往 stdout 打一个 `✓`
(`\u2713`)，而 Windows 控制台默认的 GBK 代码页里没有这个字符，`print` 当场抛
`UnicodeEncodeError`，整次跑动作废。修法是 `diag_common.apply_stream_fix()`，
现在六个探针一律从那里拿。

`probe8.txt` 是同一个脚本、同一台机器、装上 `diag_common` 之后的重跑——成功，整份 UTF-8，
`✓` 正常印出。

**这两份只有对着看才有意义**：它们是那处修复在真机上生效的唯一证据。
`diag_common.py` 的文件头、`diag_sources.py:62`、`diag_cbplan.py` 的三处注释都指着 probe7。
把它「修好」编码，等于把证据本身抹掉。

同理，`.gitattributes` 里给这个目录标了 `-text`，禁止 git 在检出/入库时改动换行符——
存档的价值在于它和当时那台机器打出来的字节完全一样。

## 想自己跑一次

探针都要联网（东财 / 巨潮 / 同花顺 / 集思录），受限网络下访问不到。
存档时**另存为一个没用过的编号**（`probeN.txt`，N 取现有最大号 +1），
不要覆盖已有的任何一份。
